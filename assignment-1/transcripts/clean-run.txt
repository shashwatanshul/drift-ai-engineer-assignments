==============================================================================
FINAL ANSWER
==============================================================================
Based on the data:

- Current read QPS is about 10,000, all hitting PostgreSQL directly.
- The product data can tolerate up to 30 seconds of staleness.
- The system must show immediate consistency for the admin session after writes, but eventual consistency is fine for others.
- The traffic is strongly skewed with a small set of hot products driving most reads.
- The Redis cluster is already available and has spare capacity.
- The cache outage must degrade gracefully to DB reads, but the DB cannot handle full load at peak, so stampede protection is needed.
- The read path is a single GET endpoint, with JSON assembled from multiple tables, where assembly is a significant latency factor.
- No new managed services are allowed this quarter, so we must reuse Redis.

Recommended caching strategy:

1. Use a Redis cache as a "cache-aside" (lazy loading) layer in front of PostgreSQL for product reads.
2. Cache full assembled JSON product documents keyed by product ID.
3. Set a TTL of about 30 seconds on cached entries to respect staleness tolerance.
4. Implement cache stampede protection using Redis locks or request coalescing to avoid DB overload on cache misses.
5. On writes from the admin tool, invalidate or update the cache immediately for that product ID to ensure session consistency.
6. Use Redis memory for caching hot keys, which will cover the majority of reads due to skew.
7. On cache miss, fetch from DB, assemble JSON, store in Redis, then return.
8. On cache outage, fallback to DB reads gracefully.

Memory cost estimate:

- Assume average product JSON size is about 5 KB (typical for product data with media URLs).
- Hot key share is high; let's say 20% of products cover 80% of reads.
- If we cache 20% of the product catalog, and the catalog size is say 100,000 products, that's 20,000 cached entries.
- Memory = 20,000 * 5 KB = 100 MB approx in Redis, which is reasonable given spare capacity.

Staleness cost:

- Up to 30 seconds stale, which is acceptable per constraints.
- Immediate consistency for admin session ensured by cache invalidation on writes.

This design balances load reduction on PostgreSQL, respects staleness and consistency constraints, uses existing Redis infrastructure, and handles traffic skew and cache stampede.

Final recommendation: Implement a Redis cache-aside layer caching assembled product JSON with 30s TTL, cache stampede protection, and write-time cache invalidation for admin sessions. This will reduce DB load by roughly 80%, use about 100 MB Redis memory, and keep staleness within 30 seconds.
