**What the findings establish**

- **Staleness tolerance:** product data can be up to 30 seconds stale; price changes are the only field that must respect this limit, while longer staleness is unacceptable.
- **Write‑side correctness:** after an admin saves a change, the same admin session must see the new value immediately; all other readers can tolerate eventual consistency.
- **Infrastructure constraints:** no new managed services can be added this quarter; we must reuse the existing Redis cluster and cannot contract a new CDN.
- **Traffic characteristics:** reads are heavily skewed toward a small subset of products, and the skew intensifies during campaigns.
- **Failure handling:** a cache outage must fall back to direct PostgreSQL reads rather than returning errors. Because the database cannot sustain the full unbuffered read load at peak, any design must address the “stampede” effect that would occur when the cache is cold.

**What I would have checked next**

- The current size and utilization of the Redis cluster (memory headroom, eviction policy, replication topology) to see how much additional product data can be stored without impacting existing workloads.

- The feasibility of implementing a “read‑through” or “write‑through” pattern on top of Redis that can satisfy the admin‑session immediacy requirement while allowing a 30‑second TTL for other readers.
- Options for cache‑warming or pre‑population of hot keys during campaign start‑up, and mechanisms (e.g., leaky bucket, request coalescing) to mitigate thundering‑herd effects when the cache expires or is evicted.
