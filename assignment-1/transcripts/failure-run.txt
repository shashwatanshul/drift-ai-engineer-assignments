FINAL ANSWER
==============================================================================
The product read API currently serves about 10,000 reads per second directly from PostgreSQL with no cache. From the internal constraints note I read, the key points relevant to caching are:

- Staleness tolerance: product data can be up to 30 seconds stale, especially for price changes.
- Correctness on write: after an admin tool saves, the next read from that session must reflect the new value immediately; eventual consistency is acceptable for other users.
- Budget: no new managed services allowed this quarter, but reusing the existing Redis cluster is approved.
- Traffic shape: strongly skewed, with a small set of products driving most reads, and skew worsens during campaigns.
- Failure policy: cache outages must degrade gracefully to direct DB reads, and the DB cannot handle full unbuffered read load at peak, so the design must prevent a cache stampede on cold cache.

Given these constraints and traffic, I recommend a caching strategy using Redis as a read-through cache with the following design:

1. Use Redis to cache product data with a TTL of about 30 seconds to respect staleness tolerance.
2. Implement cache warming and prefetching for hot keys (the small set of products driving most reads) to avoid cache stampedes.
3. On writes from the admin tool, invalidate or update the Redis cache immediately for that product to ensure session correctness.
4. For other reads, allow eventual consistency within the 30-second TTL.
5. Use Redis's built-in eviction policies and memory management to handle skew and hot keys efficiently.

Memory cost: The memory cost depends on the size of the cached product data and the number of hot keys. Assuming the average product data size is moderate (e.g., a few KBs), caching the hot set plus a reasonable buffer for other products should be feasible within the existing Redis cluster memory. The exact memory usage would be the number of cached keys multiplied by average size plus Redis overhead.

Staleness cost: Up to 30 seconds of staleness is acceptable per constraints, so the TTL can be set accordingly. This balances freshness with cache hit rate and load reduction on the DB.

This design leverages the existing Redis cluster (no new managed services), respects the 30-second staleness constraint, handles skewed traffic by focusing on hot keys, and prevents DB overload by avoiding cache stampedes. It also meets the correctness requirement for admin writes by immediate cache invalidation or update.
