FINAL ANSWER
==============================================================================
**Recommended caching design – “hot‑key, 30‑second TTL cache‑aside on the existing Redis cluster”**

| What | How |
|------|-----|
| **Cache location** | Re‑use the Redis cluster that is already provisioned (no new managed service). |
| **Cache pattern** | **Cache‑aside (read‑through)** – the API first checks Redis; on a miss it reads PostgreSQL, writes the result into Redis and returns it. |
| **Write handling** | Admin writes go straight to PostgreSQL **and** issue a `DEL key` (or `SET key … EX 30`) so the next read sees the fresh value. This satisfies the “next read from that admin session must show the new value” requirement while keeping eventual consistency for all other callers. |
| **TTL / staleness** | `EXPIRE 30` (30 s) on every cached entry. The product team tolerates up to 30 s of staleness, so this matches the constraint exactly. |
| **Eviction policy** | `maxmemory‑policy allkeys‑lru` (or `volatile‑lru` if we only set TTLs). This automatically keeps the most‑frequently‑read products in memory and evicts the long‑tail. |
| **Hot‑key protection** | Enable **request coalescing / “single‑flight”** in the application layer: when many requests miss the same hot key at the same time, only the first triggers a DB read; the others wait for the result that will be cached. This prevents a stampede when the cache is cold or after a TTL expiry. |
| **Cold‑cache fallback** | If Redis is unavailable, the code falls back to direct PostgreSQL reads (the existing behaviour). Because the cache will absorb ~85 % of the read traffic, the DB load after a cache outage will be ~1 500 reads / sec (see calculations below), which is well within the capacity of the two read replicas. |
| **Pre‑warming (optional)** | At service start‑up or after a deployment, a background job can “warm” the top‑N hot keys (see sizing below) so the first traffic burst after a cold start is already served from cache. |

---

### Why this design fits our actual numbers

| Metric (from `service_metrics`) | Value |
|--------------------------------|-------|
| **Read QPS** | 10 000 |
| **Write QPS** | 240 |
| **Hot‑key share** | 0.85 (85 % of reads hit a small hot set) |
| **Distinct product keys** | 1 800 000 |
| **Current cache hit rate** | 0 % (no cache yet) |
| **Tolerable staleness** | 30 s |

**1. Load reduction**  
If we cache the hot set that accounts for 85 % of reads, the cache will serve:

```
10 000 reads/s × 0.85 = 8 500 reads/s
```

The remaining 1 500 reads/s will go to PostgreSQL. Our read‑replica pool comfortably handles that (the current p99 latency is 180 ms with the full 10 k RPS load; at 1.5 k RPS the latency will drop to single‑digit milliseconds).

**2. Memory sizing**  

*Average response size* = 2 600 bytes (from metrics).  
*Redis overhead* (metadata, key, expiration) ≈ 500 bytes per entry (conservative).  

**Per‑entry size ≈ 3.1 KB**.

We need to hold enough keys to capture the 85 % hot share. In a typical Zipf‑like workload, the top ~5 % of distinct keys generate ~85 % of traffic.  

```
5 % of 1 800 000 ≈ 90 000 keys
Memory ≈ 90 000 × 3.1 KB ≈ 279 MB
```

Rounded up, **≈ 300 MB** of Redis memory is sufficient. The existing Redis cluster already has > 2 GB allocated, so this fits comfortably with headroom for other services.

**3. Staleness cost**  

TTL = 30 s → maximum data age = 30 s, exactly the tolerable staleness defined in `constraints.md`. No additional staleness beyond the business limit is introduced.

**4. Write‑path cost**  

Admin writes (240 writes/s) incur an extra Redis `DEL` (or `SET`) operation, which is negligible compared to the read load (≈ 0.24 % of total traffic). The latency impact on the admin flow is < 1 ms.

**5. Failure handling**  

*Cache outage*: the code falls back to DB reads. Because the cache already off‑loads 85 % of traffic, the DB sees only 1.5 k RPS, well below the peak capacity. No user‑visible errors occur.

*Cache stampede*: request‑coalescing ensures that when a hot key expires, only one DB read is issued; the rest of the concurrent requests wait for the cached result, avoiding a sudden surge to PostgreSQL.

---

### Summary of costs

| Cost type | Estimate |
|-----------|----------|
| **Memory** | ~300 MB of Redis (≈ 0.3 GB) |
| **Staleness** | Up to 30 seconds (exactly the business limit) |
| **Additional write overhead** | One extra Redis `DEL/SET` per admin write (≈ 240 ops/s) |
| **Operational impact** | No new services; uses existing Redis cluster; simple config changes (TTL, LRU, maxmemory) and a small amount of application code for cache‑aside and request coalescing. |

---

### Recommendation

Implement the **hot‑key, 30‑second TTL cache‑aside** pattern on the existing Redis cluster, with LRU eviction and request‑coalescing. This will:

* Serve ~8.5 k reads/s from memory (≈ 85 % hit rate) → > 90 % reduction in DB load.  
* Keep product data fresh within the allowed 30 s window.  
* Require only ~300 MB of additional Redis memory, well within current capacity.  
* Preserve correctness for admin writes and degrade gracefully to DB reads if Redis fails.

This design satisfies all listed constraints, matches the traffic profile, and can be rolled out with minimal engineering effort and no extra infrastructure spend.
